# Issue #102 — deep partial-audit / unresolvable subgraph advisory

**Status:** design approved · follow-up to [#89](https://github.com/2389-research/dippin-lang/issues/89) (PR #99) and the leaf/resolver hardening in [#100](https://github.com/2389-research/dippin-lang/issues/100) (PR #104).

## Problem

The cross-file `tool_access` pass (`cmd/dippin/crossfile_tool_access.go`) walks every
subgraph / `manager_loop` boundary transitively and emits **DIP146** (Hint) for a
*zero-intent* child at any depth. But the **DIP143 fallback** advisory — emitted for a
*partial-audit* or *unresolvable* child — comes from `validator.Lint`, which runs only on
the **linted entry file**. So a partial-audit or unparseable child **more than one hop deep**
(behind an already-audited intermediate) gets **no advisory**.

Example: `entry` (restricts) → `child` (full-restrict, so the `entry → child` edge is
DIP146-silent) → `grandchild` (restricts agent A, leaves tool-bearing agent B open). The
grandchild's partial-audit gap is invisible today. This was the documented "Known limitation"
in the #89 design doc (`~:191-195`) and `docs/validation.md` ("What DIP146 does NOT check").

## Approach

Have the cross-file pass emit its own boundary advisory for partial-audit / unresolvable
children at **depth ≥ 1**.

**Reuse DIP143, do not add a new code.** It is the same posture gap ("this boundary's child
restricts some-or-unknown agents; audit it") and the same `Hint` severity — only surfaced from
the cross-file pass that resolved the deep child, rather than from the entry-only per-file lint.
Reusing keeps the change to one production file: no catalog / explanation / parity /
generated-spec churn, and it matches how DIP146 is already CLI-emitted. The validator continues
to own DIP143 *detection* (wasm-safe, pure IR); its detection logic is unchanged. The only
validator edit is one clarifying sentence in the DIP143 explanation prose (`validator/explanations.go`)
noting the deep cross-file provenance, so `dippin explain DIP143` matches the deep advisory.

### Emit predicate (in `visitBoundary`)

A deep DIP143 advisory fires when **all** hold:

| Condition | Why |
| --- | --- |
| `intentSeen` | A workflow on the path restricts tools — the deep analog of validator DIP143's "workflow declares `tool_access` intent". If nothing on the path restricts, there is no restriction to escape (matches DIP146's gate). |
| `posture == posturePartial \|\| posture == postureUnresolved` | The two postures the entry-only DIP143 fallback was meant to cover. Zero-intent → DIP146 (unchanged); full-restrict / agent-less → confirmed safe (silent). |
| `depth >= 1` | **Load-bearing.** Entry-file boundaries (depth 0) already get DIP143 from `validator.Lint` (retained for partial/unresolved by the supersession rule). Emitting at depth 0 would double-flag the entry. `depth` is the depth of the workflow *containing* the boundary node, so a child's boundaries are at depth ≥ 1. |

`postureUnresolved` is emitted in the existing `child == nil` early-return branch;
`posturePartial` after `classifyChild`.

### Message / Help

Distinct wording per posture (both `SeverityHint`, both `Code: DIP143`):

- **partial-audit** — the child *was* resolved and restricts some agents but leaves ≥1
  tool-bearing agent open: "audit that agent's `tool_access`".
- **unresolved** — the child could not be resolved/parsed/was refused: "audit it manually;
  its posture cannot be verified".

This differs from the entry-file DIP143 (which can never read the child); here the deep child
*was* reached, so the advisory says what was found.

## Scope / non-goals

- One production file: `cmd/dippin/crossfile_tool_access.go` (+ a small diag constructor
  mirroring `boundaryDiag`). No new DIP code. No validator *detection-logic* change (only a
  one-sentence clarification to the DIP143 explanation prose). No wasm impact.
- **Detection, not enforcement** — no tracker dependency.
- Doc parity: update the now-closed "Known limitation" note in this folder's `2026-06-05-issue-89-design.md`
  and `docs/validation.md`.

## Edge cases (verified against the code)

- **Depth cap** (`crossFileMaxDepth = 32`): a boundary at the cap is still classified, but its
  children are never visited (`maybeRecurse` stops at `depth+1 > cap`). So the cap introduces no
  spurious `postureUnresolved`; only a genuinely unresolvable child (`resolveBoundaryChild`
  returns nil) is flagged.
- **Diamond** (two boundaries → same partial/unresolved child): one advisory per boundary —
  consistent with DIP146.
- **Supersession**: deep advisories ride in the appended `cross` findings and are never run
  through `supersedes()` (correct — partial/unresolved are never superseded). They live at
  distinct `Location`s from the entry DIP143, so there is no collision in the supersession loop.

## Tests (TDD, real `.dip` fixtures on disk)

1. `entry` (restricts) → `child` (full-restrict) → `grandchild` (PARTIAL) ⇒ one deep DIP143 at
   the `child → grandchild` boundary, Hint; zero DIP146. **The core #102 case.**
2. `entry` (restricts) → `child` (full-restrict) → `grandchild` UNRESOLVABLE ⇒ deep DIP143 at
   that boundary.
3. No double-emit: an **entry-level** partial child yields **zero** DIP143 from the cross pass
   (depth 0 guarded); the single entry DIP143 still comes from `validator`.
4. No advisory when the path has no intent (`intentSeen` false), regardless of deep posture.
5. A zero-intent deep child still yields DIP146 (not the new DIP143) — unchanged.
